Automatic data refresh

Design for BharatZero · 11 November 2026 · Approved; schedule revised by user

Keep legislative data current without manual imports. Use the existing GitHub Actions workflow to discover official records, validate them, and apply safe changes directly to the app’s PostgreSQL database.

Decisions made together

Updates run automatically without a review queue. Expand the existing GitHub Actions job. Keep TypeScript, pnpm, Prisma, and the current database.

Approaches considered

ApproachTradeoff
GitHub Actions — selectedReuses the existing daily job, works when your computer and website are off, and keeps execution logs and artifacts. Scheduled starts can be delayed by GitHub.
Render cron serviceRuns near the backend, but adds another service and its configuration.
Timer inside the web serverFew setup steps, but restarts and multiple web instances make reliable scheduling harder.

Proposed operating defaults

Run once a week on Mondays at 9:00 AM IST, with a manual “Run workflow” option for immediate refreshes. The weekly frequency was requested by you; Monday morning is the chosen default. One command runs the same pipeline locally and in GitHub. Prevent overlapping runs with workflow concurrency and a database lock. Retry transient network failures up to three times.

Discover → Fetch official records → Validate and deduplicate → Apply each source in a transaction → Save source status → Show freshness in the app

Correctness and failure behavior

  • Use stable source IDs; merge equivalent proceeding references into existing curated records.
  • Reject empty, repeated, incomplete or malformed pages, invalid dates, unexpected identifiers and conflicting duplicate records before applying a source.
  • Use bulk inserts and update only changed rows. Rerunning the same snapshot creates no duplicates and makes no unnecessary record changes.
  • Retain records absent from a source response. No blanket delete-and-reload imports.
  • Save public source snapshots and backups of affected public records before mutation.
  • Each source applies in its own transaction. A failed source keeps its last good data; other sources can succeed. The overall job still reports failure.
  • Store run history and per-source success/failure metadata in PostgreSQL, so the deployed app sees freshness without a new frontend build.
  • Distinguish last attempted check, last successful import, latest source event date and coverage. Source errors never reset successful freshness.

GitHub configuration

The workflow uses Node 22 and pnpm, generates Prisma, runs focused ingestion checks, refreshes the database, and retains public source snapshots and a JSON run summary as private workflow artifacts. It has read-only repository permissions and no automatic source-code commits.

Activation needs this workflow on the repository’s default branch and the existing app database connection stored as the GitHub Actions DATABASE_URL secret in prasiddhnaik/bharatzero. The connection string must never enter source files, reports or logs. Publishing and credential configuration will be made concrete and verified before activation.

Implementation and verification

Add a shared runner and HTTP retry/validation utilities; adapt the existing importers; add a small persistent run-history model and source-status API; update the Sources page and relevant coverage labels; expand the GitHub workflow. Add contract tests for pagination, malformed/empty responses, date handling, deduplication, idempotency, failure isolation and locking. Apply a real refresh and check the app in Browser at desktop and mobile sizes. Verify the hosted workflow after activation.

Success criteria

  • A single command refreshes all supported live sources.
  • New sessions are discovered without editing source lists.
  • Unchanged data produces zero record changes on a second run.
  • A broken source cannot erase or falsely freshen good data.
  • The app shows persisted source coverage and refresh status.
  • The GitHub schedule is enabled and a manual run succeeds against the intended database.

Primary source surfaces: Sansad bills, Parliament government-bill proceedings, Rajya Sabha questions, OGD catalogs.
